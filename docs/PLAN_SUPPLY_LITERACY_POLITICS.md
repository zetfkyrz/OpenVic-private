# План: лимиты снабжения территорий, образованность, партии и решения

Составлен 2026-10-26. Только план: код не менялся. Опирается на то, что уже есть в симуляции (см. «Что есть сейчас» в каждой части),
и на данные оригинальной игры из папки Victoria 2. Общие правила остаются: числа баланса только в `common/openvic_defines.lua`
(группы `ov_*`), детерминизм (`tools/perf_check.py`, `tools/run_tests.py`), каждое поведение, меняющее результат, поднимает
`Replay.hpp SIMULATION_VERSION` (сейчас 15), новый интерфейс — в стиле Victoria 2, проверки производительности через F12 (месячные
части уже дают пик ≈ 105–120 мс, новые месячные расчёты должны быть дешёвыми, см. [OPTIMIZATION.md](OPTIMIZATION.md)).

Порядок работ: **A (лимиты снабжения) → B (образованность) → C (партии) → D (решения) → E (отображение)**. E строится по мере
готовности A–C, не в конце.

## A. Лимиты снабжения территорий

### Что есть сейчас
- Снабжение войск идёт раз в 3 дня от стоимости создания (см. [MILITARY_SUPPLY.md](MILITARY_SUPPLY.md)); множители: поход ×1.5,
  земля врага ×2. **Лимита провинции нет**: сколько бы частей ни стояло в провинции, расход не меняется.
- Данные лимита в файлах игры уже читаются как модификаторы: `supply_limit_local_base`, `supply_limit_global_base`,
  `supply_limit_global_percentage_change` (`ModifierEffectCache`), но нигде не складываются в число для провинции.
- В интерфейсе есть место и заглушка: подпись `supply_limit` в панели провинции (`ProvinceOverviewPanel.gd`, ветка `pass`) и режим
  карты `mapmode_supply` (сейчас закрашен «ошибкой»). Потери от плохого снабжения (attrition) в `War.cpp` уже есть, но считаются
  только от доли покрытых потребностей страны, а не от провинции.

### Откуда лимит в оригинале (файлов региона для этого нет)
`map/region.txt` лишь список провинций региона. Лимит складывается из файлов:
- `map/terrain.txt`, поле `supply_limit` типа местности: равнины и фермы 10, степь 8, лес, холмы, чаща 6, горы, джунгли, болото,
  прибрежная пустыня 2;
- `common/static_modifiers.txt`: `land_province` 5, `sea_zone` 10, `coastal_sea` 10, `infrastructure` +4 (модификатор
  инфраструктуры, привязан к железным дорогам — уточнить, умножается ли на уровень), `base_values` 5 (глобальная база);
- технологии (`technologies/*_tech.txt`, `supply_limit` +0.25 или +0.5, также изобретения армии) — глобальная база и процент;
- модификаторы провинции и страны (события, решения: `add_province_modifier`).

### Модель
```
лимит провинции = (сумма локальных баз: местность + тип провинции + инфраструктура * уровень железной дороги
                   + модификаторы провинции + глобальная база страны-владельца (base_values + технологии))
                  * (1 + глобальный процент страны)
нагрузка = число полков (сухопутная часть: 1 на полк) + сумма supply_consumption_score кораблей (в оригинале «SUPPLY_LOAD»)
перегрузка = max(0, нагрузка / лимит − 1)
```
- Лимит считается для **провинции** (как в оригинале и как привязаны армии); для окон и подсказок показывать ещё среднее по региону.
- Чья земля: своя и союзников 100%, земля, куда есть военный доступ, доля `SUPPLY_LIMIT_ACCESS_SHARE` (по умолчанию 100%),
  земля врага `SUPPLY_LIMIT_ENEMY_SHARE` (по умолчанию 50%), нейтральная без доступа 0 (туда войск не пустят). Море: общее
  `sea_zone` 10; порт и морская база страны добавляют к лимиту флота стоящего в порту.
- Наказание перегрузки (все три слагаемых из defines, можно выключить любое):
  1. расход товаров растёт: множитель `1 + SUPPLY_OVERLOAD_GOODS_FACTOR * перегрузка` (это ваша идея «плохое снабжение — надо слать
     больше товаров»), применяется в `get_supply_state` (там уже множители похода и врага);
  2. уровень снабжения группы падает быстрее: цель уровня умножается на `1 / (1 + перегрузка)`; сейчас уровень общий по стране
     (`army_supply_level`), потребуется **уровень по группе** (армия, флот), хранится в `UnitInstanceGroup`, учитывать при сохранении и в
     контрольной сумме;
  3. потери людей и организации (attrition): в существующем коде `War.cpp` заменить долю страны на долю провинции
     (`rate += supply_attrition * перегрузка`), максимум `max_attrition` из `static_modifiers.txt` (там 5).
- Влияние рельефа и железных дорог на ход игры: армии распределяются по провинциям (разделить стек, идти по нескольким
  провинциям), на плохом рельефе (горы 2) большой стек не прокормить. Для ИИ нужна оценка: при выборе цели учитывать лимит
  провинции (иначе ИИ будет сажать стеки в горы).
- Когда пересчитывать: лимит меняется редко (владелец, железная дорога, технологии, события) → хранить в провинции как
  производное значение и пересчитывать в `update_gamestate` только по флагу «грязная» (не каждый день для 3000 провинций:
  сейчас `update_gamestate/map` 17 мс).

### Шаги
1. Defines: группа `ov_military` (перенести туда `ARMY_SUPPLY_*`, `NAVY_*`, добавить ключи выше), хеш и пример lua.
2. `ProvinceInstance::supply_limit` + пересчёт, сохранение в хеше состояния, тест «лимит равнин выше гор», «железная дорога поднимает».
3. Нагрузка и перегрузка по группам; уровень снабжения по группе; расход товаров с множителем перегрузки (старая страновая логика
   остаётся для ненаселённых случаев).
4. Attrition по провинции (в `War.cpp`), тест на детерминизм и на «отряд в горах несёт потери, на равнине нет».
5. Интерфейс: подпись лимита и перегрузки в панели провинции и подсказке, режим карты «Снабжение» (градиент нагрузка/лимит),
   в панели армии «снабжение: X из Y», предупреждение в ленте уведомлений.
6. ИИ: оценка лимита при выборе провинции для стека.
Оценка: симуляция 2–3 дня работы, интерфейс 1–2 дня.

## B. Образованность (грамотность) населения

### Что есть сейчас
- У попа есть `literacy` (0.01–1), начальное значение из истории страны (`CountryInstanceManager.cpp`). **Динамики нет**: грамотность
  после старта не меняется (нет ни роста, ни спада).
- Читают грамотность: политика (рост либерализма `LIBERAL_LITERACY_BONUS`), сознательность (`CONSCIOUSNESS_LITERACY_GROWTH`),
  шанс изобретения (`INVENTION_LITERACY_CHANCE`), статический модификатор `average_literacy` страны.
- Бюджет образования есть (ползунок, зарплаты священников и учителей `education_salary_base_by_pop_type`, фактические расходы),
  но **грамотность от него не зависит**.
- В данных оригинала: `common/defines.lua` — `BASE_CLERGY_FOR_LITERACY 0.005`, `MAX_CLERGY_FOR_LITERACY 0.04`,
  `LITERACY_CHANGE_SPEED 0.1`; модификаторы `education_efficiency` (технологии культуры, +10% за шаг) и
  `education_efficiency_modifier` (реформы `issues.txt`: +10%, +15%, +20%, +15%), `literacy_con_impact` (свобода печати).

### Модель роста (месяц, на каждый поп)
```
доля_духовенства  = клирики провинции / население провинции (по оригиналу, в границах BASE..MAX)
фактор_духовенства = clamp((доля - BASE) / (MAX - BASE), 0, 1)
финансирование    = ползунок образования * (фактически уплачено / запланировано)    // 0..1
эффективность     = 1 + технологии (education_efficiency) + законы (education_efficiency_modifier) + модификаторы страны
рост = LITERACY_CHANGE_SPEED * фактор_духовенства * финансирование * эффективность
       * (1 - грамотность) ^ DIMINISHING_EXPONENT       // чем выше грамотность, тем медленнее
       * доступность(тип попа, культура)                  // принятые культуры 1, непринятые меньше, рабы 0
```
- Разница с оригиналом (уточнить по wiki при реализации): формулу сверить, опорные числа — те же defines. Если проверить нечем,
  принять эту, она в любом случае управляется defines.
- **Спад**: при нулевом финансировании и малом духовенстве грамотность медленно падает (`LITERACY_DECAY`, по умолчанию 0 — как в
  оригинале; можно включить для сложности).
- Миграция и слияние попов: грамотность смешивается взвешенно по размеру (проверить `PopDynamics` — новые поколения не должны
  обнулять накопленное).
- Деньги замыкают контур: расходы образования уходят в зарплаты духовенства и учителей → богатеющее духовенство растёт (повышение
  из других страт) → растёт фактор духовенства. Учителя как ограничение: «ёмкость школ» = число клириков × учеников на клирика
  (`STUDENTS_PER_TEACHER`), финансирование выше ёмкости ничего не даёт — вторая причина строить церкви и держать классы.
- Технологии и законы дают только множители (`эффективность`), без них кривая роста плоская; ограничение «уровень технологий
  открывает следующий порог»: например, максимум грамотности по уровню школ (`LITERACY_CAP_BY_...`), чтобы начальная эпоха не
  выходила за 100%. Реализовать как множитель до порога, потом технологии поднимают его.

### Последствия грамотности (кроме уже существующих)
- очки исследований: в оригинале очки зависят от духовенства и грамотности — подключить в `ResearchDynamics`;
- сознательность растёт быстрее (уже есть), поэтому образование даёт политическое давление: радикализация, рост либералов и
  социалистов (интересный выбор «просвещать или нет»);
- производительность: рост эффективности РГО и фабрик от грамотности работников (малые проценты, `LITERACY_OUTPUT_BONUS`);
- призыв: грамотные солдаты лучше (организация), офицеры требуют грамотности;
- статус цивилизации (для варианта «цивилизации по уровням» из ваших планов).

### Шаги
1. Defines `ov_population` (или `ov_education`): `LITERACY_*`, `STUDENTS_PER_TEACHER`, `LITERACY_DECAY`, экспоненты.
2. Месячная часть `population/PopDynamics`: `update_literacy()` — **считать по провинциям/типам агрегатами, а не по каждому попу**
   (перф: месячные части уже по 10 мс), записывать по попам простым умножением; детерминизм по порядку.
3. Финансирование: связать с `actual_education_spending / projected` и со слайдером; тест: нулевой бюджет — нет роста, полный — рост.
4. Подключить `education_efficiency` технологий/законов (проверить, что модификаторы уже суммируются в страну).
5. Исследования и политика: подключить в `ResearchDynamics`, в подсказки.
6. Интерфейс: окно населения (уже показывает грамотность), прогноз роста в подсказке бюджета образования (+X% в год), панель
   страны: график грамотности по годам; режим карты «Грамотность» (новая кнопка или меню режимов).
7. Баланс: ориентиры взять из начальных данных игры (история стран задаёт грамотность 1836 года), к 1936 при обычной игре средние
   значения должны подойти к историческим (сверить с вами). Проверять прогоном `-e 3650` и таблицей по странам (добавить в
   `BALANCE_TARGETS.md`).

## C. Партии (из оригинальной игры) и интересная политика

### Что есть сейчас
- Партии страны читаются из файлов (`CountryParty`: идеология, даты, политики), правящая партия задаёт активные политики партии
  (`rule_set`), у поп есть голоса и поддержка идеологий (наш `PoliticsDynamics`, месячный, 92 мс — сначала оптимизировать).
- Выборы работают (`holds_elections`, `term_duration`), победитель меняет правящую партию; в окне политики уже есть данные.
- `mapmode_party_loyalty` и «верхняя палата» — заглушки/частичные.

### Что довести до оригинала
1. Партия как набор позиций по всем группам политик (`PartyPolicyGroup`) и реформ; смена правящей партии меняет активные политики
   и модификаторы страны (налоги, тарифы, воинственность, цензура).
2. Реформы (`issues.txt`): голосование «за» и «против» по весам избирателей (`get_group_support` уже считает поддержку); порог
   принятия, верхняя палата как у оригинала (`upper_house`), политический капитал не нужен.
3. Партии в разных странах: даты возникновения и роспуска партий уже есть; добавить создание новой партии при росте
   идеологии без партии (`no_party_share` уже считается).
4. Страна без выборов: партия задаётся правительством, смена при переворотах.
5. Окно «Политика»: диаграмма голосов, партии с процентами, правящая выделена, подсказки с позициями партий.

### Как сделать политику интереснее (предложения, по убыванию пользы к цене)
1. **Удовлетворённость бюджетом**: каждая страта/профессия оценивает бюджет (солдаты и офицеры — военный, духовенство и
   клерки — образование, капиталисты — тарифы и субсидии, рабочие — соцрасходы); отклонение от желаемого двигает лояльность
   партии и воинственность. Бюджет перестаёт быть только числами.
2. **Политический капитал** (ограниченный ресурс): пополняется от бюрократов и престижа, тратится на реформы и решения;
   нельзя принять всё сразу. Контрреформы дороже. Мягкий предел вместо жёсткого запрета.
3. **Фракции внутри партии** (умеренное и радикальное крыло): колебания поддержки, расколы, коалиции; правительство держится,
   пока поддержка парламента выше порога, иначе роспуск и новые выборы.
4. **Кампании**: за деньги и престиж можно «обхаживать» группы избирателей (покровительство, подарки), но коррупция растёт, что
   режет эффективность налогов и администрации. Баланс «купить голоса — потерять доходы».
5. **Реформа и откат**: реакционные попы радикализуются после реформ (мятежи, перевороты армии при высокой лояльности
   офицеров и недовольстве), поэтому реформы идут в темп, который можно проиграть.
6. **Образование и идеология**: грамотность и сознательность двигают сдвиг идеологий (часть B) — реформы приходят снизу, а не только из
   решений игрока.
7. **Война и политика**: усталость от войны двигает поддержку правящей партии; победы дают престиж; поражения — смену правительства.
8. **Национальные и религиозные партии** внутри сложных стран (Австрия, Россия): сепаратизм, требования автономии.
9. **СМИ и цензура**: свобода печати (`literacy_con_impact`) ускоряет рост сознательности: выбор «стабильность или прогресс».
Для старта разумно взять пункты 1 и 7 (малый объём, сильный эффект) и 2 (если решения требуют капитала).

### Шаги
1. Инвентаризация: что из `PartyPolicy`, `Reform` и их эффектов реально применяется в `CountryInstance` (проверить, что смена политик
   меняет модификаторы), список пробелов.
2. Довести цикл «партия → политика → модификаторы страны → результат» и показать в окне.
3. Лояльность/удовлетворённость по страте и профессии (пункт 1), режим карты лояльности `mapmode_party_loyalty`.
4. Усталость от войны → поддержка партии (пункт 7).
5. Политический капитал (если принимаем).
Оценка: 3–5 дней симуляции и окно политики.

## D. Решения (decisions) оригинальной игры, события пока не нужны

### Что есть сейчас
- Файлы `decisions/*.txt` читаются в `Decision` (потенциал `potential`, `allow`, `ai_will_do`, `effect`); `PARSE_SCRIPTS("decision")`
  вызывается при загрузке. **Исполнения нет**: условия не проверяются каждый период, эффекты не применяются, окна нет.
- В файлах 152 решения. Самые частые элементы (число упоминаний): `tag` 178, `owns` 171, `prestige` 121, `has_country_flag` 97,
  `set_country_flag` 91, `add_core` 60, `government` 51, `any_pop` 49, `relation` 39, `has_global_flag` 37, `add_country_modifier` 29,
  `remove_core` 28, `militancy` 27, `consciousness` 24, `country_event` 18 (события — пока заглушка), `change_tag` 14, `political_reform` 13,
  `annex_to` 5, `secede_province` 6, `release_vassal` 3. Крупнейшие файлы: `ACW.txt` (836 строк), `NationalUnification.txt` (811),
  `Germany.txt`, `France.txt`, `Political.txt`, `RUS.txt`.

### Что нужно
1. **Состояние страны для решений**: флаги страны и глобальные флаги (`set_country_flag`, `has_country_flag`, `set_global_flag`),
   временные модификаторы страны и провинции с длительностью (`add_country_modifier`, `duration`), история выполненных решений;
   всё хранится в `InstanceManager`/стране (не в `static`), попадает в хеш и сохранение (реплей: действие игрока `take_decision`).
2. **Условия** (`potential`, `allow`): те, что уже есть для условий событий и реформ (`ConditionScript`), плюс недостающие из списка
   выше: `owns`, `tag`, `government`, `relation`, `in_sphere`, `war`, `is_greater_power`, `civilized`, `average_consciousness`,
   `ruling_party_ideology`, `invention`, `year`, `exists`…
3. **Эффекты** (`EffectScript`): сначала самые частые — `prestige`, `add_country_modifier`, `any_pop` (militancy, consciousness),
   флаги, `add_core`, `remove_core`; потом территориальные (`secede_province`, `release_vassal`, `annex_to`, `change_tag`,

4. **ИИ**: `ai_will_do` (вес, `ConditionalWeightFactorMul` уже есть) — раз в месяц ИИ берёт решение с наибольшим весом.
5. **Игрок**: окно решений (в оригинале `decisions_window`/`political_decisions`, интерфейс есть в `interface/*.gui`), кнопка принять,
   подсказки с условиями (какие выполнены, какие нет); лента уведомлений «стало доступно решение».
6. **Не поддерживаемое — не молча пропускать**: неизвестное условие/эффект → решение отключено, предупреждение в журнале и
   список в отладчике (так видно покрытие).
7. Событие внутри эффекта (`country_event`) пока пишет запись в журнал и ничего не делает.
