# Оптимизация симуляции: куда смотреть, что делать первым и как ничего не сломать

Документ для тех, кто оптимизирует код **без доступа к игре** (только C++ и headless-симуляция). Данные ниже — из реального
прогона (скорость 3, 60 с, ENG, отчёт в [docs/perf/](perf/)) и из headless-профиля `-F`.

## 1. Что сейчас нагружает и откуда скачки

Одна игровая «день» (тик) = **тик симуляции + update_gamestate + обновление интерфейса**, и всё это идёт в **главном потоке
Godot в одном кадре**. Поэтому раз в игровой день кадр растёт со ~16 мс до 100–140 мс (на скорости 3 это раз в 1.5 с — это и есть
«скачки»). Игра при этом занимает в среднем **1.2 ядра из 16** (пик 2.1): параллельны только отдельные части тика, и они короткие.

Среднее время частей в мс за день (headless, 120 дней; в игре чуть больше из-за интерфейса):

| часть | мс | потоки | что это |
|---|---|---|---|
| `tick/map_tick (provinces, pops)` | 23 | пул | провинции и попы |
| `tick/market (orders)` | 22–36 | пул по товарам | заказы рынка |
| `update_gamestate/map (provinces, states)` | 17 | **1 поток** | производные данные провинций |
| `update_gamestate/countries` | 9 | **1 поток** | производные данные стран |
| `tick/countries after the map` | 6.4 | пул | бюджет, запасы, снабжение |
| `update_gamestate/modifier_sums` | 3 | 1 поток | суммы модификаторов |
| интерфейс (`UnitBanners._refresh`, `ModelManager._sync_units`) | 4.5 + 2.3 (макс. 17 и 11) | главный | только в игре |

Раз в месяц (в первый день месяца) к этому добавляется:

| часть | мс | потоки |
|---|---|---|
| `tick/monthly/politics` | **85–92** | **1 поток**, самая большая часть |
| `tick/monthly/pop dynamics` | 11–13 | 1 поток |
| `tick/monthly/country AI` | 7–10 | 1 поток |
| `tick/trade network` (пересборка маршрутов) | до 8, в игре на первом тике до 100 | 1 поток |

Итого: **месячный тик ≈ 105–120 мс сверху** (отсюда самый длинный тик 184 мс), а **каждый день ≈ 55–85 мс** только на
симуляцию, из них около 40 мс последовательные (`update_gamestate` и месячные части).

## 2. Куда смотреть

- Профиль «по частям»: `python tools/perf_check.py --profile` или `openvic-simulation.headless -b <Vic2> -e 120 -F`
  (строки `PROFILE …`, те же названия, что на вкладке «Симуляция» отладчика F12). Новая часть для замера — одна строка
  `OV_PROFILE_SCOPE(tick_profiler, "имя");` в [InstanceManager.cpp](../extension/deps/openvic-simulation/src/openvic-simulation/InstanceManager.cpp).
- Внутри части — настоящий профилировщик по строкам: Visual Studio → Debug → Performance Profiler → CPU Usage на
  `openvic-simulation.headless.exe -b <Vic2> -e 120` (сборка RelWithDebInfo уже с PDB). Смотрите «Hot Path» и «Functions: Self time».
- Отладчик F12 в игре (`game/src/UI/Session/PerfDebugger.gd`): вкладки «Процессор» (ядра и потоки), «Тест» (60 секунд на скорости,
  отчёт в `%APPDATA%\OpenVic\perf\`). Кому-то с доступом к игре стоит повторять тест после ваших правок.
- Файлы: [PoliticsDynamics.cpp](../extension/deps/openvic-simulation/src/openvic-simulation/politics/PoliticsDynamics.cpp),

## 3. Что оптимизировать первым (самый малый риск, результат бит-в-бит тот же)

Правило: **результат вычислений не меняется ни на один бит**, меняется только способ его получения. Проверяется командой
`python tools/perf_check.py` (см. раздел 5).

### 3.1. `PoliticsDynamics::monthly_update` (92 мс, главный месячный всплеск), ожидаемо ×3–10

Для **каждого попа** каждый месяц код делает то, что зависит только от типа попа или от идеологии (файл
`politics/PoliticsDynamics.cpp`, строки 142–265):

1. `base_leaning(defines, type.get_identifier(), strata)` — десятки сравнений строк и создание `std::vector` на каждый поп.
   → Один раз за вызов `monthly_update` построить таблицу `PopType → вектор (индекс идеологии, вес)` и брать из неё.
2. Для каждой идеологии 7 сравнений строк `name == "reactionary"` и т. п. на каждый поп.
   → Один раз получить для каждой идеологии небольшое перечисление (`enum`) и делать `switch`.
3. `std::vector<double> shares(...)`, а в лямбде `spread` ещё `std::vector<double> weights(...)` **на каждую группу реформ на каждый поп**.
   → Вынести векторы за цикл попов и только очищать/перезаполнять (`assign`).
4. В `spread` для каждого пункта реформы пересчитывается `closeness(positions[i], position)`, зависящая только от числа
   пунктов группы и номера пункта.
   → Таблица `closeness[option_count][option][ideology]`, посчитанная один раз. Порядок суммирования
   `weights[option] += shares[i] * closeness` **не менять** (иначе округления дадут другой результат).
5. `country.get_modifier_effect_value(*cache.get_strata_effects(type.strata).get_vote())` на каждый поп.
   → Один раз на страну и страту (три значения).

Не менять: типы (`double`, `float` в `parse_unsafe(static_cast<float>(...))`), порядок операций, порядок обхода стран и
провинций.

### 3.2. Такая же «гигиена» в других месячных частях

`PopDynamics.cpp` (13 мс), `country AI` (7–10 мс), `RebelDynamics` (2–4 мс): искать `std::vector`/`memory::vector`/`std::string`/
`std::map` **внутри** циклов по попам и провинциям (выносить за цикл, `reserve`), сравнения строк-идентификаторов в горячих циклах
(заменять индексом, он уже есть у типов: `type.index`, `ideology.index`), повторные вызовы одного геттера с тяжёлым
вычислением (кэшировать в локальную переменную).

### 3.3. Профиль по строкам для `map_tick`, `market`, `update_gamestate`

Они уже разбиты на части, но внутри каждой есть что убрать тем же способом. Сначала Performance Profiler, потом правка самого
горячего места, потом `perf_check`. Правок «на глаз» по этим частям не делать: там параллельный код (см. раздел 6).

## 4. Что можно, но уже с осторожностью (проверка `perf_check` обязательна, плюс чтение кода на гонки)

- **Месячную политику по странам в пул потоков.** Страны независимы (каждая пишет только свои попы и свою страну), но
  выборы пишут в общий `notification_log` и вызывают `set_ruling_party`: собирать результат в локальные структуры и применять
  после цикла в порядке стран. Результат не должен зависеть от числа потоков (`-j 1` и `-j 4` дают одинаковые CHECKSUM).
- **Баланс пула на рынке.** Рынок идёт «по товарам»: один тяжёлый товар держит весь пул. Раздавать товары по оценке стоимости
  (по числу заказов вчера), порядок обработки на результат не влияет (в `CLAUDE.md`: «порядок ордеров от потоков зависит и на
  результат не влияет»).
- **`update_gamestate`**: он каждый день пересчитывает производные данные (суммы модификаторов, данные провинций, стран), которые
  нужны интерфейсу. Часть можно считать лениво (только то, что показывает открытое окно) — но это уже изменение поведения
  интерфейса: проверять только в игре.

## 5. Как ничего не сломать

Команды (папка Victoria 2 и собранный headless нужны; сборка: `python tools/run_tests.py --build`):

```bash
python tools/perf_check.py --save-baseline   # ДО правок, на чистом коммите: сохраняет контрольные суммы каждого дня (docs/perf/baseline_checksums.json)
python tools/perf_check.py                   # ПОСЛЕ правок: те же суммы, с 1 и 4 потоками; код выхода 1 = поведение изменилось
python tools/perf_check.py --profile         # времена частей тика за 120 дней
python tools/run_tests.py                    # все автотесты (≈1.5 мин): детерминизм, сохранение/загрузка, сохранение денег
```

Базовые контрольные суммы текущего коммита уже лежат в репозитории (`docs/perf/baseline_checksums.json`, симуляция версии 15).
Правило коммита: **оптимизация ничего не меняет в результатах**; если `perf_check` показал отличие — это ошибка в оптимизации
(или вы случайно поменяли геймплей: тогда отдельный коммит с новым baseline и своим описанием).

Что ломают чаще всего (из `CLAUDE.md` и `docs/BUGS_FIXED.md`):
- Неинициализированная локальная переменная (`bool x;`) — делала симуляцию недетерминированной. Всегда `= false`/`= 0`.
- Порядок обхода `unordered_map`/`unordered_set` не фиксирован: нельзя от него зависеть в вычислениях, результат должен быть тот же при любом порядке.
- Параллельные колбэки рынка пишут **только в свой слот**; чужому попу — только атомарное прибавление.
- Деньги двигать только через места с `MoneyLedger::record` (иначе тест сохранения денег упадёт).
- `fixed_point_t` умножается/делится только на целые ≤ 4 байт; арифметика с `double` в политике уже есть — не смешивать порядок.
- Состояние, которое помнят между днями, держать в `InstanceManager`, а не в `static`, иначе тест детерминизма упадёт.
- Одна и та же сборка с любым `-j N` обязана давать те же строки CHECKSUM.

## 6. Разделить нагрузку по ядрам: симуляция отдельно, интерфейс отдельно (следующий этап, нужен доступ к игре)

Сейчас главный поток делает всё. Целевая схема:

1. **Поток симуляции** владеет `InstanceManager` и выполняет `tick()` (внутри — свой пул, как сейчас). Главный поток Godot
   рисует кадры и обрабатывает ввод.
2. **Команды игрока** уже идут через очередь `GameAction` (`queue_game_action`), их выполняет симуляция в начале тика —
   менять почти не надо.
3. **Чтение состояния интерфейсом** — главная трудность: окна читают симуляцию напрямую (`PlayerSingleton`, `*Menu.cpp`,
   `MapView`, подсказки). Пока тик идёт в другом потоке, такое чтение — гонка. Варианты, по возрастанию объёма работы:
   - блокировка «симуляция занята»: тик держит эксклюзивный замок, геттеры интерфейса берут общий; кадр ждёт максимум
     время одного тика (это уже убирает только часть скачков);
   - **двойная буферизация**: после тика `update_gamestate` + «снимок» нужных данных (цвета карты, значения верхней панели,
     списки окон) в структуру, интерфейс читает только снимок; нужно переписать геттеры по окнам по одному;
   - выполнять `update_gamestate` и обновление интерфейса по частям по кадрам (бюджет 4–5 мс на кадр), чтобы не было
     одного кадра в 100 мс.
4. Порядок работы: сначала всё из раздела 3 (быстрее сам тик), потом `update_gamestate` по частям, потом отдельный поток.

Любая работа по пункту 6 проверяется в игре (отладчик F12: вкладки «Процессор» и «Тест»), заранее её не проверить.

## 7. Промпт для помощника (скопировать целиком)

```
Ты оптимизируешь симуляцию OpenVic (C++20, extension/deps/openvic-simulation). Игры и Godot у тебя нет, только headless-сборка и
папка Victoria 2. Прочитай CLAUDE.md, docs/OPTIMIZATION.md, docs/BUGS_FIXED.md. Главное требование: результат симуляции не
меняется ни на бит.

1. Собери headless (python tools/run_tests.py --build), сними базу: python tools/perf_check.py --save-baseline (если docs/perf/
   baseline_checksums.json уже совпадает с коммитом, достаточно python tools/perf_check.py).
2. Сними профиль: python tools/perf_check.py --profile; найди самые тяжёлые части (сверху: tick/monthly/politics, tick/market,
   tick/map_tick, update_gamestate/map).
3. Оптимизируй по одной части за раз, начиная с PoliticsDynamics::monthly_update (раздел 3.1 документа): таблицы вместо
   сравнений строк, вынос векторов из циклов, кэширование. Не меняй типы, порядок операций и порядок обхода.
4. После КАЖДОЙ правки: сборка, python tools/perf_check.py (должен быть OK), потом python tools/run_tests.py. Если есть
   отличие — откати правку, не подгоняй baseline.
5. Один коммит на одну часть: git commit -s, в сообщении: что было (мс до/после по --profile) и что сделано. Сначала коммит в
   сабмодуле (ветка diplomacy-actions, push), потом указатель в основном репозитории (origin master). Не коммить
   game/addons/godot_ai и правки game/project.godot от godot-ai.
6. Не распараллеливай и не меняй модель данных без явной просьбы. Любую гонку проверяй -j 1 и -j 4.
```
